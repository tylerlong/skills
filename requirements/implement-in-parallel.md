# implement-in-parallel requirements

1. Load the `implement` skill before starting and use it as the Child Ticket worker contract. If it is unavailable, return **Do Not Start** without starting a Batch Run.
2. Accept exactly one GitHub Parent Ticket in the current Git repository and coordinate its implementation through one isolated Batch Run.
3. Use only these outcomes: **Do Not Start** when the run cannot begin and no Batch artifacts were created; **Resumable Stop** when a started run cannot progress, after checkpointing its state and preserving its unfinished artifacts; and **Complete** only after all Batch-scope work is satisfied or delivered, every ticket in scope is closed, final tracker and local-`main` work is finished, and successful owned artifacts are cleaned.
4. Give an existing broken-`main` repair absolute priority. While a Delivery Turn is in `repair`, its owner performs only that repair; every other coordinator starts no new Batch Run and suspends started ordinary work at a recoverable boundary with its artifacts preserved.
5. If the Parent has an existing Batch checkpoint, reconcile every recorded claim with current Git and GitHub state and resume from the first unfinished action. Reuse valid commits, Repair proof, review, verification, PR, merge, and CI evidence when still bound to the unchanged candidate; never repeat valid completed work. Preserve ambiguous state and return **Resumable Stop** instead of guessing.
6. For a new run, read the repository instructions, the complete Parent Ticket, and every direct native Child Ticket with its readiness and native blockers. Native GitHub relationships are authoritative; do not infer them from ticket bodies or change ticket bodies, labels, assignments, or relationships. Do not comment on tickets or change their state before finalization.
7. Freeze the Parent's direct Child Ticket numbers as the Batch scope when the run starts. Refresh and use the current state of only those tickets throughout the run; never add or remove tickets from that scope.
8. Treat a closed Child Ticket as satisfied. An open Child Ticket is eligible only with `ready-for-agent`, and is runnable only when each native blocker is closed or its in-scope blocker commit is integrated into the Batch Branch. If a new run has no direct children, no open eligible children, or no initially runnable child, return **Do Not Start** before creating Git artifacts.
9. Preserve the caller checkout, its local `main`, and Installed Skills. Fetch `origin/main`, record that commit as the immutable Batch Base and initial Review Base, and create one owned Batch Branch and external Batch Worktree from it. Perform all coordination, integration, validation, push, and PR work in that Batch Worktree, and treat every other task worktree as foreign.
10. Maintain at most one sparse Parent-specific checkpoint in the Git common directory and outside version control. Record only the fixed scope, Batch and Review Bases, owned artifacts, exact commit-bound progress and evidence, Delivery Turn state, used recovery allowances, and next action. Update it whenever resumable progress, evidence, or Delivery Turn ownership changes and before every **Resumable Stop**; treat Git and GitHub as authoritative for their own state.
11. Reconcile an ambiguous external write before repeating it, and never resubmit accepted asynchronous work. Retry or observe transient external work only for a bounded period. Do not retry an explicit permission, credential, infrastructure, human, or other rejection; return the appropriate stopped outcome with the exact next action and preserve recoverable state.
12. Schedule runnable children only by native blockers and available worker capacity. Run independent children concurrently without predicting file overlap; the coordinator alone manages dependencies, worker starts, and integration.
13. Immediately before dispatch, refresh the selected Child Ticket, Parent Ticket, and blockers. Start an owned Child branch and worktree from the current Batch Branch commit containing all integrated blockers. Give the worker only its Parent and Child context, repository instructions, exact starting commit, owned paths, the `implement` contract, and the orchestration limits; do not give it sibling identities or communication duties.
14. Each Child Ticket worker follows `implement`, except it runs focused checks instead of canonical full repository verification and uses characterization-first regression evidence for a pure refactor. It stays in its owned worktree, returns exactly one final clean ticket commit with its evidence, and does not push, mutate GitHub, perform combined Batch review, or coordinate with other workers.
15. As each worker finishes, validate that its handoff, commit, evidence, and worktree are bound to the reported commit without normally rerunning unchanged focused checks. Integrate one Child Ticket commit at a time into the Batch Branch, checkpoint its exact integrated commit, and immediately use freed capacity for newly runnable work.
16. Do not predict conflicts or prerequisites. Return an actual integration conflict and all accepted behavior to the same Child Ticket worker, update its branch from the current Batch Branch, and require one replacement ticket commit with focused evidence. If a Child Ticket exposes an undeclared prerequisite, pause it; satisfy an in-scope prerequisite through the normal Batch flow, or report an out-of-scope prerequisite without changing the issue graph and continue independent work.
17. The coordinator never writes implementation, conflict-resolution, or repair code. Give accepted review findings and implementation-caused verification, PR-CI, or main-CI failures to a dedicated repair worker from the exact failing commit.
18. Before repair edits, bind trustworthy evidence of the reported problem to the exact starting commit or reproduce it when necessary. The repair worker runs the exact acceptance check first after its change, then the smallest affected focused checks, and returns one separate clean repair commit with the pre-repair evidence, post-repair acceptance result, affected checks, limitations, commit, and clean state. The worker never runs canonical full verification; the coordinator validates the commit-bound proof without normally repeating unchanged checks. Use at most one shared fallback attempt for essential context loss or a genuinely different approach after strategy exhaustion, never an identical blind retry.
19. When an exact CI failure is proven implementation-caused but cannot be reproduced locally, bind the exact CI log and commit, run the closest local checks, state that the exact failure was not reproduced locally, and keep exact-head CI as the acceptance gate. Do not change code for a merely suspected transient failure.
20. Do not open a Batch PR while any in-scope Child Ticket is runnable or still being integrated. When nothing else can currently progress, continue to delivery only if the Batch Branch contains an undelivered integrated change; otherwise checkpoint the blocker and return **Resumable Stop**.
21. Determine the repository's canonical full verification before delivery; if none can be identified reliably, checkpoint the exact decision needed and return **Resumable Stop**. On the exact Batch head, run the `code-review` skill against the Review Base and resolve every accepted finding through a repair worker until review is clean, then run canonical full verification. Any candidate change invalidates both gates; after a verification repair, repeat review and full verification.
22. Refresh the in-scope tickets and blockers after the exact candidate passes both gates. If another child is now runnable, schedule it and repeat the invalidated gates. Otherwise push the Batch Branch, open or update one non-draft PR to `main` for that delivery cycle without auto-closing tickets, confirm its head is the reviewed and verified commit, and require CI green for that exact head. An implementation-caused PR-CI repair restarts review, full verification, push, and exact-head CI; an external failure returns **Resumable Stop**.
23. Acquire the repository-wide Delivery Turn only after the exact PR head has passed review, full verification, and PR CI. Acquisition must be atomic and nonblocking, with a complete owner identity and `delivery` or `repair` phase. A normal `delivery` owner blocks only another delivery acquisition, not ordinary Batch work. If the turn is busy or ownership is ambiguous, checkpoint and return **Resumable Stop** immediately without waiting, stealing, deleting, or replacing it.
24. Inherit a Delivery Turn only for the same Parent when the recorded task is conclusively inactive and the checkpoint, branch, PR, exact head, phase, and merge state agree. Do not infer inactivity from age or a missing local process. Abandon only a user-named run after proving its PR and head were not merged; an uncertain or completed merge retains ownership until reconciled.
25. While owning `delivery`, refresh the Batch scope again. If a child is runnable, release the turn, implement and integrate it, update the same PR, and repeat every invalidated gate. Fetch `origin/main`; if it advanced beyond the Review Base, incorporate that exact commit into the Batch Branch, use a worker for any actual conflict, advance the Review Base to the incorporated main commit while leaving the Batch Base unchanged, release the turn before pushing, and repeat review, full verification, and exact-head PR CI. Review from the new Review Base must exclude upstream-only changes.
26. Reconfirm the exact green PR head, merge it through GitHub with a merge commit without deleting its branch, fetch `origin/main`, and prove the fetched commit is the merge result and contains the Batch head. Retain the Delivery Turn while observing CI for that exact remote-main commit. If a merge response is uncertain, keep ownership until the PR and `origin/main` prove whether the merge occurred.
27. If exact remote-main CI proves an implementation failure, change the Delivery Turn to `repair` and keep it owned. Start a repair-only branch and worktree from the exact broken `origin/main`, give one dedicated worker only the failure evidence and restoration scope, and never automatically roll back or include unrelated feature work.
28. Apply the same Repair proof, combined review, canonical full verification, exact-head PR-CI, merge, ancestry, and exact-main-CI gates to every broken-main repair candidate. Keep all ordinary Batch work suspended and retain `repair` ownership until the exact repaired `main` is green. A further implementation failure starts another repair-only cycle within the shared fallback allowance; exhaustion or an external or human blocker returns **Resumable Stop** while preserving ownership and repair artifacts.
29. Only after exact remote-main CI is green, release the Delivery Turn and begin finalization. Comment on and close each delivered in-scope Child Ticket with its PR, merge, verification, and exact-main-CI evidence. Comment on each excluded, paused, or blocked in-scope Child Ticket with its blocker and next action and leave it open. Preserve every ticket's labels and native relationships. Add one Parent summary and close the Parent only when every ticket in the fixed Batch scope is closed.
30. After releasing the Delivery Turn, fetch `origin/main` and fast-forward the local `main` mirror only when doing so preserves all local work and requires no merge, reset, overwrite, commit, or push. Otherwise preserve the local state, checkpoint the exact action needed, and return **Resumable Stop**.
31. Remove only successfully delivered artifacts owned by the run, including its remote Batch Branch only after merge and exact-main-CI proof. Preserve every blocked, unfinished, ambiguous, and unrelated artifact. If some Batch-scope tickets remain open, retain the checkpoint and return **Resumable Stop** after cleaning only the delivered cycle. Return **Complete** and remove the checkpoint only when the entire fixed Batch scope and every finalization obligation are complete.
